01 / Direction & scope

Build a software factory with a dependable core.

Launch Up should translate a business brief into a validated application specification, assemble proven modules, generate only missing capabilities, test the result, and deliver a reproducible release. Your existing React dashboard becomes the operating console. The first revenue product should be a limited set of excellent outcomes, expanded as delivery becomes repeatable.

Recommendation: choose the 12-month path if you are learning while building. A six-month result should be a supervised pilot. More time buys testing, template depth, operational reliability, and design refinement; it does not guarantee frontier-model capability.

Planning assumption: one primary builder working about 20–25 focused hours per week, using coding assistants, with occasional experienced review. That is roughly 1,040–1,300 hours over a year before holidays and interruptions. If starting from zero programming knowledge, allow more time. The schedule is a planning estimate, and acceptance gates determine release readiness.

What the repository already gives you

React 19, Vite, TypeScript, Tailwind, 20 tab components, shared modals, domain types, theme tokens, and a broad product vocabulary. Business state is mostly in-memory; deployment, training, and agent actions are simulated.

What must become real

Identity, durable data, asset intake, specifications, template assembly, isolated execution, verification, release management, cost accounting, and team permissions. Existing architecture documents describe intent beyond implemented capabilities.

Repository assessment carried forward from the source review in this conversation. No running-app or build validation is implied. This document is a proposed implementation plan, not a claim that these systems exist.

Initial scope: business websites and service-company management software. Add more business modules after successful pilots. Android, marketing execution, custom customer models, and complex SaaS architectures enter later service tracks. Every track needs its own acceptance criteria.

02 / Learning curriculum

Learn by producing the next piece of Launch Up.

Do not finish a year of courses before building. Each learning block should end in a small working deliverable. Spend approximately 30% of the early weeks studying, 50% implementing, and 20% testing and documenting. Gradually move time from courses to real failures and improvements.

04 / Docker & distributed execution

Portable projects. Independent workers. Shared control.

1. Control planeConsole, API, identity, specifications, budgets, job state
2. Worker fleetIsolated build/test jobs; temporary workspaces and previews
3. Model serviceLocal or hosted inference; GPU-aware request queue
4. Client runtimeReleased containers and persistent data, independently operated

Docker contract for every project: a multi-stage Dockerfile, local Compose configuration, environment-variable schema, health endpoint, explicit persistent volumes, migration command, lockfile, test command, release manifest, and restore instructions. Deliver source plus an image digest and operational documentation. Keep customer secrets outside images and build arguments.

Build once and promote the tested image digest through preview, staging, and production. Include dependency inventory and provenance where supported. A container packages runtime dependencies; it does not automatically configure DNS, TLS, email delivery, database backups, or mobile signing. Docker attestations

Isolation must match the trust level

Docker is the packaging baseline, but containers share a host kernel. Run ordinary project containers with non-root users, limited capabilities, read-only filesystems where practical, bounded CPU/RAM/disk/PIDs, separate networks, and scoped secrets. Rootless Docker reduces privilege exposure; it is not a complete boundary for hostile builds. Docker security · Rootless mode

AI-generated code, repository install scripts, and uploaded templates are untrusted execution. Place their builders on separate disposable worker VMs, with a sandbox runtime such as gVisor where compatible. Never mount the production host’s Docker socket into a client workspace. Keep a trusted build supervisor outside that workspace. Restrict egress and destroy temporary credentials after completion. gVisor

Design for simultaneous team members now

  • Workspace identity: organizationId + projectId + jobId + attemptId. Separate clone/worktree, filesystem, network, preview URL, and test database for each job.
  • Editing: every specification has a revision. Updates include the expected revision; stale writes return a conflict. Freeze a revision for each build.
  • Source: task branches and pull requests. Use a merge queue; one migration owner/integrator resolves shared schema changes. Do not let several agents write into the same checkout.
  • Scheduling: workers advertise capabilities such as linux-build, android-build, browser-test, and gpu-inference. Admit jobs only when resources and budget are available.
  • Fairness: per-organization and per-project concurrency limits, fair queues, priority, cancellation, timeout, retry budget, and maximum queued work.
  • Recovery: leases and heartbeats identify abandoned work. A fencing token rejects results from an expired worker. Steps use idempotency keys; external side effects require deduplication and reconciliation.
  • Events: save state plus an outbox event transactionally. Stream persisted events to the UI with sequence IDs so reconnects do not lose progress.
  • Releases: serialize production promotion per project/environment. Approval binds to the spec revision and artifact digest; a changed artifact requires a new decision.

Distributed computing means distributing jobs first. Multiple laptops or servers can build different projects. That does not combine their RAM/VRAM into one fast model. Keep model inference centralized or replicated; consider model sharding only for a later, measured need.

05 / Reuse & product quality

Make modern design repeatable.

Use four layers: UI primitives → business modules → product blueprints → custom extensions. Names, labels, fields, and themes are configuration. Scheduling conflicts, inventory reservations, financial rules, and workflow permissions are tested business logic.

Brief + assets → Requirements → AppSpec@revision
  → Compatible template/module lock
  → Deterministic assembly + bounded custom patches
  → Container build + acceptance/visual/security checks
  → Preview → approved release digest → monitored deployment

AppSpec records entities, stable field keys, relationships, pages, roles, row scopes, workflow transitions, theme tokens, integrations, and acceptance criteria. JSON Schema checks shape; semantic validation checks compatibility and business rules. Never execute arbitrary code embedded in configuration.

A template manifest records version, source digest, stack profile, required modules, supported configuration, licence, migrations, tests, and screenshots. Use curated references and licensed assets to create distinct visual directions. Keep global design tokens separate from page compositions so outputs do not all become the same dashboard with new colours.

Design system work

Typography scales, spacing, colour/contrast, grids, reusable layout patterns, light/dark modes, focus states, reduced motion, loading/skeleton states, empty/error states, and readable dense tables. Establish at least three deliberate design directions before selling broad customization.

Feedback and verification

Capture approved screenshots and user tasks. Compare generated pages at multiple widths and with long text, large datasets, missing images, validation errors, and slow networks. Let clients approve actual previews before production promotion.

Release gates for each generated application

  • Correctness: specified workflows and permission boundaries pass; no known critical defect. Test authorization on the server, not only hidden buttons.
  • Responsive behaviour: exercise 360/390, 768, 1024, and 1440 px widths; no unintended page overflow, clipped actions, or unusable touch targets.
  • Accessibility: target WCAG 2.2 AA; automated checks plus keyboard, focus, screen-reader, and zoom checks. An automated score alone is not conformance.
  • Performance: target field p75 LCP ≤2.5 s, INP ≤200 ms, CLS ≤0.1 for relevant pages. Use lab tests before traffic exists, then measure real users. Core Web Vitals
  • Operational readiness: health checks, rollback procedure, database migration compatibility, backup restore evidence, logs, and owner/contact information.
  • Supply chain: scan code/dependencies/images and secrets; triage findings. “Scanner passed” is not proof of zero vulnerabilities.

Application rollback cannot undo arbitrary database changes. Prefer expand/contract migrations and test old/new application compatibility during rollout. Extract reusable modules only after removing client information, confirming reuse rights, and testing a second business configuration.

06 / Execution roadmap

Choose a horizon. Preserve the quality gates.

The options below change the deliverable scope, not the standard of correctness. The detailed sequence is the recommended 12-month path, measured from your actual start date.

12 months · production foundation

Two polished product families, concurrent hosted workers, reliable releases, measured local-model routing, and supervised expansion into one adjacent service.

Allow time for pilot feedback and recovery drills. Android, marketing, and model training remain separate acceptance tracks.
01FOUNDATIONS

Stabilize the prototype and learn the web core

Pin tools and dependencies; document existing mock behaviours; learn Git/TypeScript/HTTP. Establish shared UI tokens, real routes, basic checks, and a clean local startup.

Gate: another person can clone, start, and navigate the project using written instructions.

02PERSISTENCE

Implement identity, tenancy, and durable records

Create API, PostgreSQL migrations, organizations/memberships, client/project CRUD, role checks, and audit events. Wire one complete frontend journey before expanding.

Gate: records survive restart; cross-tenant access and unauthorized writes fail.

03SPECIFICATION

Make client intake and AppSpec real

Business brief, asset uploads, versioned requirements, missing-information workflow, schema validation, and acceptance criteria. Manual spec editing remains available.

Gate: three sample businesses produce valid, reviewable specifications with unresolved questions exposed.

04FIRST DELIVERY

Ship the first containerized marketing-site pipeline

Versioned template, deterministic assembly, Docker build, browser checks, artifact store, preview URL, and delivery bundle. Start with one hosting target.

Gate: a fresh environment launches the exact tested release; a failed build never appears successful.

05BUSINESS CORE

Build one reusable service-management application

Contacts, service jobs, appointments, notes/files, roles, filtering, exports, and configurable forms. Keep core rules in modules and theme/layout settings in the spec.

Gate: three distinct service businesses work from one blueprint with no manual core rewrites.

06CONTROLLED AI

Add the model gateway and bounded coding jobs

Local/cloud adapters, usage ledger, retrieval, structured output, explicit tool permissions, patch proposals, test-and-repair limits. Run first supervised design-partner previews.

Gate: unsupported tasks escalate or stop; budgets and cancellation work. This is the six-month pilot scope.

07COLLABORATION

Make jobs durable and team work conflict-safe

Persist steps, leases, fencing, idempotency, revision checks, branch ownership, and per-tenant quotas. Wire real event streams into Agent Company and Project Canvas.

Gate: simultaneous users cannot overwrite specs silently; worker termination does not duplicate a release.

08HOSTED PILOT

Move execution to isolated worker hosts

Separate control/build environments, registry/storage, backups, scoped credentials, measured queue limits, and client handover documentation. Refine templates through pilot feedback.

Gate: two separate workers deliver independent projects; a restore drill succeeds; operating costs are visible.

09LOCAL AI

Benchmark Liquid and coding baselines; train selectively

Build a held-out dataset and compare task quality, memory, latency, and escalation. Fine-tune one narrow task if justified, then evaluate its quantized version.

Gate: the candidate improves cost per accepted task without unacceptable regressions.

10QUALITY

Strengthen design, accessibility, and release confidence

Curated design directions, visual baselines, browser/device coverage, realistic load tests, module upgrade paths, independent security/design review.

Gate: selected product families meet published acceptance targets; unresolved limitations are documented.

11CAPACITY

Scale from measurements and add one adjacent service

Load-test a provisional five-user/five-project scenario, tune fair scheduling and inference pooling, and add either Android delivery or a bounded automation service.

Gate: declared concurrency meets queue/latency budgets; the new service has its own delivery and recovery tests.

12OPERATIONS

Launch the stable service and close the learning loop

Track delivery margin, defects, support time, template reuse, and model costs. Drill incident recovery, document runbooks, and schedule verified upgrades.

Gate: repeatable paid delivery for the supported catalogue. Broader autonomy follows demonstrated reliability.

Six-month scope: months 1–6, supervised. Eight-month scope: add collaboration and hosted pilot. Ten-month scope: add measured local AI and deeper quality work. Twelve-month scope: add capacity testing, one adjacent service, and operational hardening. If a gate fails, reduce scope or move the date.

07 / Liquid AI assessment

A strong candidate for small, bounded jobs.

Documented capability Liquid’s current catalogue includes LFM2.5-1.2B-Instruct, LFM2.5-2.6B, smaller variants, and larger/MoE models. The 2.6B documentation describes native tool calling and a 128K maximum context. That context limit is a model capability, not a suitable starting configuration for your laptop. Model catalogue · 2.6B documentation

The LFM2 technical report describes a hybrid of gated short convolutions and attention, selected with hardware-aware architecture search. Its training includes large-scale pretraining, distillation, and post-training. These efficiencies are already embodied in released checkpoints: you can adapt a checkpoint without reproducing that foundational training. The older LFM2 report should not be used as a specification for every newer LFM2.5 variant. LFM2 technical report

Use a gateway so the model can change without altering business modules. Local deployment reduces outside data transfer, but “local” does not guarantee privacy: logs, telemetry, uploaded training examples, and remote fallbacks still need explicit policies.

08 / Memory & inference research

Optimize the bottleneck you actually have.

Inference memory ≈ weights + attention KV cache
                 + recurrent state (for hybrid models)
                 + activations / runtime workspace + concurrency overhead

Training memory additionally includes gradients, optimizer state,
saved activations, adapters, and framework overhead.

At four bits per parameter, raw weights alone are approximately 0.6 GB for 1.2B parameters, 1.3 GB for 2.6B, and 3.5 GB for 7B, using decimal GB. These are arithmetic lower-bound estimates, not observed VRAM requirements. Actual quantized formats add metadata and mixed-precision tensors. A model with few active MoE parameters may still need far more total weight storage.

TechniqueWhat it improvesAdoption decision
Short context + retrievalLess prompt processing and cache allocationUse first Retrieve only relevant contracts, examples, and files. Measure lost-context failures.

KV-cache quantizationMemory that grows with attention context and concurrencyUse supported formats after baseline; re-evaluate long-context retrieval and structured output.

Supporting references: PEFT quantization, vLLM prefix caching, speculative decoding. Recommendations above are Launch Up-specific engineering judgments.

TurboQuant: useful research, with a precise scope

Google’s March 2026 article describes vector/KV-cache compression and reports at least 6× KV-memory reduction in its evaluated setting, plus up to 8× acceleration for an attention-logit computation on H100. Those figures are not an 8× end-to-end application speedup or a 6× reduction in all model memory. Google Research

The linked paper abstract reports quality neutrality at 3.5 bits per channel and some degradation at 2.5 bits in its experiments; the blog summarizes results differently. Preserve benchmark conditions when comparing claims. Neither source establishes universal losslessness for Launch Up workloads. TurboQuant paper

Integration experiment Current vLLM documentation includes TurboQuant quantization and attention-backend APIs, so it is not accurate to label it “paper only.” However, the sources reviewed do not establish a validated LFM2.5 + RTX 3050 + chosen-runtime combination for this project. Pin a runtime release, confirm architecture/kernel support, and test on your tasks before enabling it. vLLM TurboQuant API · Attention backend

For a short-context hybrid model, the attention cache may be a smaller part of total memory. Therefore my inference is that reducing model size, prompt length, and simultaneous requests may help your laptop more initially. TurboQuant does not compress all recurrent state or eliminate training optimizer/activation memory.

Liquid DSpark: a separate speed experiment

Liquid’s August 2026 release supplies draft checkpoints for selected LFM2.5 models and describes llama.cpp/SGLang integration. It reports up to 3.18× GPU throughput and 2.87× on-device improvement under its tested conditions. This targets speculative decoding, not the same bottleneck as KV compression. Verify the exact target/draft/runtime pairing and benchmark warm/cold latency, acceptance rate, and memory. DSpark release

Experiment order: baseline → shorter context → weight quantization → supported cache options → DSpark/speculation → batching on a hosted server. Change one variable at a time. Keep TurboQuant behind a feature flag until it improves quality-adjusted results.

09 / Training & evaluation

Train a useful specialist, then prove the improvement.

Start with requirements-to-AppSpec or template selection. These have structured outputs and clear checks. Avoid training a broad “Astra + Claude + Gemini replacement.” For a small model, excellent performance on a constrained task is a defensible goal; general frontier parity is not an assumption.

  1. Define the task and rejection cases. Write examples of supported, ambiguous, conflicting, and unsupported requests. A correct “needs clarification” is a success.
  2. Create an evaluation set before training. Start with roughly 100–200 varied examples as an experiment. Reserve unseen businesses and template families; do not put renamed copies of training examples into the test set.
  3. Establish baselines. Deterministic rules, prompted small model, and prompted model with retrieved examples. Record schema validity separately from semantic correctness.
  4. Curate a pilot dataset. Approximately 500–2,000 carefully checked task examples is a starting experiment, not a guarantee. Store provenance, permissions, schema version, accepted answer, and verifier evidence.
  5. Train one adapter. Use a supported SFT/LoRA recipe. Begin with short sequences and small batches; gradient accumulation/checkpointing may trade memory for time. Measure memory in a tiny smoke run before a long job.
  6. Evaluate before and after quantization. Include unknown workflows, permission traps, malformed assets, long inputs, and requests outside the supported catalogue.
  7. Deploy in shadow mode. Compare proposals without allowing production actions, then canary a limited task. Store model, adapter, prompt, template, and dataset revisions.

Liquid maintains fine-tuning recipes, including SFT + LoRA and evaluation examples. PEFT documents quantized adapter training generally; do not assume every Liquid architecture, module name, or training backend supports every QLoRA recipe unchanged. Training a GGUF file directly is not the standard adapter-training workflow. Liquid fine-tuning repository · PEFT guide

Free training is experimental capacity

Colab’s free GPU availability and runtime limits vary, and sessions can end. Use interactive notebooks, checkpoint frequently, and persist artifacts you can resume elsewhere. Do not use free notebook sessions as a dependable production inference service or bypass quotas. Training availability cannot be part of a client SLA. Colab resource limits

On your laptop, inference is the primary use. A small adapter-training experiment may fit with suitable settings, but no exact capacity is promised. Keep model training, Android builds, browser testing, and inference from competing simultaneously for limited RAM. Rent a bounded GPU session only when the experiment and dataset are ready and a spending cap is set.

11 / Economics & first steps

Spend on accepted outcomes.

Track three budgets separately: Launch Up’s own development, each client delivery, and ongoing client operation. The last includes hosting, storage, backups, observability, communication services, and support—even when inference has no external API fee.

Delivery cost = API tokens + local/GPU compute + build/test compute
              + retries/review + allocated template maintenance

Monthly operating cost = control plane + workers + inference
                       + database/storage/backups + support

Training break-even tasks = training/setup cost
                          / net saving per accepted task

For illustration only: if training/setup costs 100 cost units and saves 0.02 units per accepted task after retries and review, break-even is 5,000 tasks. This is arithmetic, not a provider price estimate. If quality regresses, the saving may disappear.

  • Use templates/configuration before model calls. Keep standard CRUD, permissions, calculations, and workflow transitions deterministic.
  • Cache reusable build layers and approved artifacts with correct version/tenant boundaries. Expire unused previews.
  • Budget model output, retries, and concurrent jobs. A job reaching its budget stops or requests a deliberate extension.
  • Separate interactive previews from long training/batch tasks. Shared GPU queues should prioritize the product’s agreed service targets.
  • Buy hosting before promising availability. Upgrade hardware only after measured utilization and revenue support the cost.
